## Appendix A: maintainability checklist


# Maintainability review

The goal is code a tired human can read cold in two months and change without fear. Correctness still matters, but this review asks a different question: is this as simple as it can be, and will it be easy to work with?

## 1. Decide whether this code is important

Run the review if any of these are true:

- The repo ships to customers (a product, an app, a public API, a package other people install).
- A failure costs money, data, or trust: payments, auth, migrations, background jobs, anything on a deploy path.
- Other code depends on it: shared modules, libraries, core domain logic.
- The user says it matters, or asks for a review.

Skip it for scratch folders, one-off scripts, notebooks, demos, and anything the user calls quick, temporary, or throwaway. If you can't tell, look at the repo: CI config, tests, a deploy setup, or a real package manifest means important. When skipping, don't mention the skill.

## 2. Read before judging

Read the whole change and the code around it. Trace the real flow from entry point to side effect. Check how the rest of the repo already does things, because the codebase's existing conventions win over your preferences. A suggestion that ignores how the code is actually called is worse than no suggestion.

## 3. What to look for, in priority order

**Delete first.**
- Dead code, unused parameters, commented-out blocks, stale flags.
- Abstractions with one user: interfaces with one implementation, factories that build one thing, config for values that never change, wrappers that only pass through.
- Hand-rolled versions of things the standard library, the platform, or an installed dependency already does.
- Code duplicated from a helper that already exists elsewhere in the repo.

**Make it obvious.**
- Names say what a thing is or does, in the domain's words. `retryDelayMs`, not `val2`. `isTrialExpired`, not `check`.
- One function, one job. If describing it needs "and", split it. If it needs scrolling, it's probably doing too much.
- Flatten nesting with early returns. Replace boolean-flag parameters that switch behavior with two clearly named functions.
- Magic numbers and strings get a named constant, unless the value is self-explanatory where it sits.
- Prefer boring code. Clever one-liners, metaprogramming, and dense chained expressions cost the next reader more than they save.

**Make it safe to change.**
- Side effects (network, disk, DB, global state) sit at the edges, not buried inside logic that looks pure.
- Errors are handled where something can actually be done about them. No swallowed exceptions, no empty catch blocks, no "log and continue" when continuing corrupts state. Error messages say what failed and with what input.
- Related code lives together. A change to one behavior should touch one place, not five files.
- Types and data shapes are explicit at module boundaries.
- Non-trivial logic (branches, parsing, money, permissions) has at least one test that would fail if it broke. Flag missing tests on critical paths; don't demand tests for trivial code.

**Comments explain why, never what.**
- Keep or add comments for non-obvious decisions, workarounds, and constraints ("Stripe sends this webhook twice; dedupe on event ID").
- Delete comments that restate the code, and any comment the code now contradicts.

## 4. What not to do

- Don't rewrite working code to match your taste. Every change needs a concrete readability or safety payoff.
- Don't add layers, patterns, or dependencies in the name of cleanliness. Simpler means fewer moving parts.
- Don't strip input validation at trust boundaries, security checks, or error handling that prevents data loss, even if it looks verbose.
- Don't nitpick formatting a linter or formatter should handle.
- Don't pad the review. Five real findings beat twenty trivial ones.

## 5. Output

List findings worst first. For each one:

- **Where:** `path/to/file.ext:line`
- **Problem:** one sentence on what makes it hard to understand or change.
- **Fix:** the concrete change, with a short before/after snippet when it helps.

Tag each finding **must fix** (will confuse or break things for the next person) or **worth doing** (a clear improvement, not urgent). End with one or two sentences on the overall state of the code. If it's already clean, say so in one line and stop.

If you're reviewing your own change before finishing, apply the must-fix items yourself instead of listing them, then briefly say what you changed.

## Appendix B: careful-review checklist


# Careful review

Keep the code small. Be thorough in checking it. A short diff is good; a short review is how bugs ship. This skill doesn't change how much code you write (ponytail still decides that). It changes how hard you look before saying "done."

## 1. Decide whether this code is important

Run the review if any of these are true:

- The repo ships to customers (a product, an app, a public API, a package other people install).
- A failure costs money, data, or trust: payments, auth, user data, migrations, background jobs, deploy paths.
- Other code depends on it: shared modules, libraries, core domain logic.
- The user says it matters, or asks for a review.

Skip it for scratch folders, one-off scripts, notebooks, demos, and anything the user calls quick, temporary, or throwaway. If you can't tell, look at the repo: CI config, tests, a deploy setup, or a real package manifest means important. When skipping, don't mention the skill.

## 2. Read everything the change touches

This is where shortcuts cause the most misses. Before judging anything:

- Read every changed file in full, not only the diff hunks.
- For each changed function, grep its callers and read them. A fix that's right for one caller can break another.
- Follow data from where it enters (request, form, file, env var, queue message, webhook) to where it's used (query, shell, file path, HTML, log, external API).
- Read the tests for the changed code, or notice that none exist.

Don't review from memory or from the function name. If you didn't open it, you don't know what it does.

## 3. Go through every item on this list

Check each item explicitly. Mark it n/a if it doesn't apply, but don't skip it silently.

**Security**
- **Injection:** user input reaching SQL, shell commands, file paths, regexes, templates, or `eval` without parameterizing or escaping.
- **Auth:** is every new endpoint, route, or action protected? Does it check that *this* user owns *this* record, not just that someone is logged in?
- **Secrets:** keys, tokens, or passwords in code, logs, error messages, client bundles, or URLs.
- **Untrusted data:** XSS from rendering user content, SSRF from fetching user-supplied URLs, path traversal from user-supplied filenames, unsafe deserialization.
- **Exposure:** API responses or logs that leak more fields than needed (password hashes, emails, internal IDs, stack traces).
- **Dependencies:** any new package. Is it maintained, needed, and the real package name (no typosquat)?

**Correctness**
- **Edge inputs:** empty, null/undefined, zero, negative, huge, unicode, duplicates, wrong type.
- **Failure paths:** what happens when the network call, DB write, or file read fails halfway? Is anything left partially written?
- **Concurrency:** two requests at once, double-clicks, retried webhooks, race between check and write.
- **State and data:** migrations that lose or lock data, missing transactions around multi-step writes, cache that goes stale.
- **Time and money:** time zones, DST, floating point for currency, rounding, off-by-one on ranges and pagination.
- **Contracts:** changed function signatures, API shapes, or DB columns that other code or clients still rely on.

**Operations**
- Errors are caught where something useful can happen, and logged with enough context to debug, without logging secrets.
- New config or env vars are documented and fail loudly when missing.
- Anything that can't be undone (deletes, sends, charges) is guarded.

## 4. Verify, don't assume

- Run the tests. If there are none for a risky path, write the smallest test that would fail if the logic broke, and run it.
- Run the linter and type checker if the repo has them.
- If you claim something is safe ("input is validated upstream"), point to the line that proves it.
- If you couldn't verify something, say so plainly. Don't phrase a guess as a fact.

## 5. Keep fixes simple

Finding problems isn't a license to over-build. Fix each issue with the smallest correct change: a parameterized query, one guard in the shared function all callers go through, one ownership check. No new layers, frameworks, or "security utilities" unless the repo already has that pattern. Never remove existing validation, auth checks, or error handling to make code shorter.

## 6. Output

List findings worst first:

- **Where:** `path/to/file.ext:line`
- **What:** one sentence describing the issue.
- **How it breaks:** the concrete input or situation that triggers it.
- **Fix:** the change, with a short snippet when it helps.

Tag each **critical** (security hole, data loss, or customer-facing breakage), **should fix**, or **minor**. Then add one line listing what you checked and found clean, plus anything you couldn't verify. If nothing turned up, say what you checked in that line and stop.

If you're reviewing your own change before finishing, fix critical and should-fix items yourself, rerun the checks, then report what you changed.
